## Combined with original Apollo, exactly what is supported

[R070](NATIVE_SYN_APPLICATION_FIELDS.md) mapped GCloud outgoing SYN field4=llGameID, **field5=iUnitID**, field6=iClientType from the original sender and serializer. [R071](SYN_ATTRIBUTE_SUPPLIERS.md) established the discovery path uses unit1/client type101. [R072](RPC_DOMAIN_UNIT_SOURCE.md) found an RPC initializer able to parse a numeric domain component into unit ID, and `CTDir::Initialize` passes a 10-byte route literal. [R073](R073_RPC_INITIALIZATION_ORDER.md) proves a unit can be set during `RpcConnector::Init` **before address lookup**; a later address reply is not proven to set it.

**The strongest current explanation is a second connector with a different unit ID and a different named route.** This is an evidence-supported *mechanism*, not demonstrated execution of the CTDir/version/puffer caller on the phone. The real phone's SYN field5 changes; its actual numeric value, domain, route content, connector identity, whether GCloud vs another stack actually emitted it, and accepted ACK/session are still unverified.

R071's **client-type-field6-only** explanation is now disfavored for this phone run because field6 is **not listed among changed non-route fields**. A separately changed key/security field1–3/7 is also not *observed by this exact byte comparison*, which is reassuring but insufficient to claim cryptographic/session compatibility or ACK acceptance.
